**4. P1：可靠性与运行安全**

**P1-1：隔离密码校验和文档解析的阻塞工作，约 2–4 人日。**

[登录接口](../trpc_service/admin/session_router.py#L50) 在异步处理函数内同步执行 Argon2id，而且校验时已持有账号行锁；未知账号也会执行同样的 KDF。当前有账号失败锁定，但没有看到针对来源、未知账号和全局 KDF 并发的统一限制。账号锁定不能代替资源保护。[知识解析](../trpc_service/storage/knowledge.py#L520) 同样在异步链路直接执行 PDF/DOCX 解析；抽取字符数上限在完整解析后检查，无法阻止解析阶段资源占用。

将密码校验移入有界执行池，并限制并发、排队长度、请求体及密码长度；调整事务边界时保留失败计数的原子性，处理验证期间密码被重置的竞争。文档解析放到有 CPU、内存、时间限制的进程或任务执行器，增加页数、解压后体积等前置约束。Python 官方说明阻塞计算会延迟同一事件循环的其他任务，CPU 密集任务可通过进程执行器隔离；线程适合部分阻塞 I/O，但不提供可强制终止的资源隔离。[Python 事件循环文档](https://docs.python.org/3.12/library/asyncio-eventloop.html)

验收：并发错误登录和复杂文件解析期间，普通管理查询与进程健康检查仍满足已约定延迟；队列满返回明确状态；账号锁定/解锁及密码轮换竞争测试通过。

**P1-2：拆分进程就绪与全链路可用性，约 2–3 人日。**

[`/ready`](../trpc_service/web/app.py#L213) 同时依赖数据库与至少一个活跃 Worker。所有 Worker 暂时离线时，Gateway 会整体退出服务，管理 API 也受影响。[节点计数](../trpc_service/agent/nodes.py#L157) 先加载全部历史节点再在 Python 中统计，健康探测成本随历史节点增长。[部署清单](../deploy/kubernetes/application.yaml) 给 Gateway 配置了探针，而 Worker、Channel Runtime 和 scaler 没有探针；这些后台角色启动后主要等待停止信号，进程存活不足以证明工作循环健康。

将控制 API readiness、消息接收容量和端到端 Agent 可用性拆开表达；主库能可靠入队且积压未超预算时，是否继续接收消息应成为显式策略。活跃节点计数下推 SQL，并限制查询耗时。后台进程增加工作循环心跳、任务异常监护和 HTTP/exec 探针，liveness 不依赖外部数据库短暂可用性。[Kubernetes 探针语义](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-probes/)

验收：停掉全部 Worker 后仍能进入管理端恢复容量；故意终止一个后台工作循环能被发现并重启；SQL 暂时断连不会造成集群连锁重启。

**P1-3：让 Channel Runtime 具备明确的归属与故障接管，约 4–7 人日。**

当前渠道部署为 `replicas: 1`、`Recreate`，升级和实例故障会中断长连接。两个 [Binding Supervisor](../trpc_service/channels/wecom_runtime.py#L270) 都按全部活动绑定建连，未见跨进程 Binding 所有权租约。直接增加副本会产生同账号重复连接以及投递节点不持有相应 Transport 的风险。

先增加 Binding 级所有权、租约、generation 与排空转移；投递领取必须匹配当前 Transport 所有者。再依据不同 IM SDK 的同账号连接语义决定主备或分片部署，避免把单副本改成双副本就视为完成高可用。

验收：持有连接的 Pod 被杀后，其他实例在商定时限接管；旧实例恢复后不能继续发送；滚动升级没有已持久化消息丢失，重复投递遵循已有 UNKNOWN/幂等规则。

**P1-4：明确回复投递的顺序保证，约 1–3 人日。**

Agent Task 已按 routing key 阻止早期未完成任务后的任务执行；[DeliveryTaskQueue](../trpc_service/channels/delivery.py) 只对可领取的 Outbox 排序，没有同会话“前序未完成”约束。当前序回复退避或投递并发大于 1 时，后序回复可能先到。`sequence_no` 唯一约束本身不提供发送顺序保证。

根据产品需要选择按会话、请求或 Binding 的顺序边界；为该边界增加前序约束/分区发送器，并明确 DEAD_LETTER/UNKNOWN 是否阻塞后续消息。验收覆盖第一条限频、第二条已就绪、多投递实例竞争及人工重放场景。

**P1-5：将生产配置变成可验证的运行契约，约 2–4 人日。**

[Settings](../trpc_service/config/settings.py) 默认允许 InMemory、`secure_cookies=False`，且没有按部署环境进行统一生产约束。当前 Kubernetes 清单面向受控部署，未提供 Ingress/TLS 和 NetworkPolicy。[pgvector 初始化](../trpc_service/storage/adapters/pgvector.py#L47) 在应用启动执行 extension/table/index DDL；[S3 初始化](../trpc_service/storage/adapters/s3.py) 也可能创建 bucket，扩大了应用身份的权限和启动依赖。

增加明确的 production 配置模式：校验持久化事实库、TLS/Cookie、Secret 引用、租约与心跳关系；完成初始化后限制 bootstrap 管理令牌的长期使用。迁移身份负责 DDL，运行身份只验证 schema 兼容并访问必要资源；bucket 建立移到基础设施流程。角色只初始化所需后端，避免 Gateway 因可选向量服务初始化失败而完全不可用。

验收：不安全或不兼容配置在启动/发布时给出可操作错误；运行数据库账号无 DDL 权限仍可正常工作；生产清单通过网络访问和证书检查。

**6. 知识库和 Agent 效果优化**

知识库 HTTP 上传当前同步等待解析、embedding 和索引完成，见 [knowledge_router.py](../trpc_service/storage/knowledge_router.py#L151)。已有 INGESTING/READY/FAILED 等持久状态，可在此基础上增加独立入库任务：上传返回 `202 + job_id`，执行端续租、分阶段 checkpoint、重试和取消，前端展示进度与失败原因。把旧向量清理、失败补偿、卡住的 INGESTING 恢复纳入持续 reconcile。预估 3–5 人日。

目前 Runtime 会检索 Memory，但仓库运行链路未见自动 Memory 写入、Summary 生成与读取闭环；`derived_outbox` 提供了扩展位置，尚未看到对应 Memory/Summary 生产者和消费者。应在文档中明确“已有存储接口”和“已具备自动长期记忆”之间的交付边界。若该能力是目标，采用 Session 提交后产生派生任务、按事件序号推进、幂等生成摘要和记忆；建立过期、删除、个人信息保留及跨群作用域规则。预估 4–7 人日，排在核心可靠性之后。

检索效果不能用覆盖率代替。建立包含中文短问题、同义表达、跨文档问题、无答案问题和权限隔离的固定评测集；记录 Recall@k、引用正确率、拒答合理性、端到端耗时和单问 token/embedding 成本。先比较现有固定字符切块与按标题/段落切块，再决定是否引入混合检索和 reranker。reranker 会增加成本与延迟，只有评测证明收益后再启用。预估首批评测集与基线 2–4 人日。

**7. 可观测和运维优化**

**先修 trace 关联，约 1–2 人日。** [HTTP middleware](../trpc_service/web/app.py#L83) 从请求头手动截取或随机生成 `trace_id` 用于日志，却没有把提取的 OTel parent context 传给新建的 `gateway.handle` span。因此该日志标识与实际 span 的 trace ID 不能保证一致。应先标准提取上下文、建立 span，再读取真实 trace ID 写日志；验证非法 traceparent 的降级，并让 SQL 任务与投递持续传递同一上下文。[OTel Context Propagation](https://opentelemetry.io/docs/concepts/context-propagation/)

Worker/Channel 已通过 OTLP 上报指标，不能把“没有 HTTP /metrics”视为“没有监控”。当前 SDK Resource 也会自动生成进程实例 ID，本次未确认多实例指标身份缺失。应在真实 Collector 中验证跨进程汇总、重启后的 counter 行为以及 dashboard/告警使用的标签。

现有 [告警规则](../trpc_service/config/observability/prometheus-rules.yaml) 主要覆盖执行错误、投递错误和治理拒绝。新增最老任务等待时间、待处理/运行/死信数量、租约续期失败、各渠道连接状态、已持久化消息的回复延迟、连接池等待、事件循环延迟及知识入库失败。租户成本和高基数详情优先保留在 SQL/日志，避免为每个 request/session 创建指标标签。

已有 [备份/恢复脚本](../dev/scripts/backup.sh) 和 [恢复说明](故障运维与恢复.md)，下一步补自动调度、离机保管、恢复演练报告与实际 RPO/RTO。为 Session event、Inbox、Outbox attempt、审计、usage、过期登录 Session、旧节点记录制定不同保留期。清理前保留消息幂等窗口与审计要求，避免删除后使旧 IM 消息重新执行。存储高可用、PITR、对象版本控制和告警接收端需结合实际生产环境交付，不能从当前本地清单推定已具备。

**9. 测试和交付门禁**

当前整体覆盖率达到门槛，但 `agent/queue.py` 为 76.67%、`postgresql_approval.py` 为 76.22%、`agent/audit.py` 为 57.78%。这些值指示需要检查的路径，并不等同于模块质量排名。优先验证并发和故障不变量，再决定哪些分支值得补测。

建议将已有 `dev/scripts/ci.sh` 接入仓库托管 CI；本仓库未发现 `.github/workflows`，无法确认远端是否另有流水线。分层运行：每次提交执行格式、类型、单测；合并前执行真实 PostgreSQL/Redis/S3 与迁移；定期执行镜像/依赖扫描和恢复演练。外部组件测试不能在发布门禁里静默跳过。开发客户端测试必须沿用 `dev/project_root.sh` 的导入路径。

必须补充的场景：

| 场景 | 必须保持的不变量 |
| --- | --- |
| 多连接并发领取同一 Session | 有效提交者只有一个，旧 fencing token 无法提交 |
| Worker 在模型返回后、提交前/后崩溃 | 状态可恢复，已记录工具副作用不能被盲目重复执行 |
| 首条 IM 回复限频，后续回复已就绪 | 符合声明的顺序策略，UNKNOWN 不自动重发 |
| 两个租户共用相似资源 ID | 数据、密钥、审批、向量命中、下载均不串租户 |
| MCP 重定向、DNS 切换、超大响应 | 出口策略与资源限制生效，失败不会占用无限时长 |
| 知识入库中断与重复提交 | 状态可收敛、向量可重建、检索只返回授权的有效版本 |
| 超过 100 条资源的管理端 | 翻页、筛选、编辑和错误提示可用 |
| 迁移与备份恢复 | 空库升级、旧版本升级及隔离恢复后均可完成一条消息链路 |

压测分两层：先用确定性 Runner 测平台队列/数据库/租约容量，再在明确额度内测真实模型和 IM；分别记录等待、执行、检索和投递耗时。已有 `capacity_check.sh` 使用的是输入假设估算，应补实际负载数据，不能用其输出替代压力测试。容量规划应同时约束模型 token 配额、IM 限流和数据库连接数。

**10. 分阶段实施顺序**

| 阶段 | 主要交付 | 退出条件 | 工作量估算 |
| --- | --- | --- | --- |
| A：正确性闭环 | P0-1/P0-2、格式基线、生产配置初步校验 | SSRF 回归通过；允许的事实后端全链路通过；静态门禁全绿 | 5–8 人日 |
| B：运行稳定 | 阻塞工作隔离、健康检查、投递顺序、trace 修正、关键并发测试 | 故障注入符合预期；日志可串联；后台循环失败可发现 | 7–12 人日 |

阶段估算已考虑部分工作重叠，不应把所有单项估算再次累加。以 2 名熟悉项目的工程师投入为前提，可先安排约 3–5 周完成 A/B/C，再根据租户规模决定 D 的范围；真实供应商联调和基础设施审批可能增加日历时间。

每项优化都应以独立、可回滚的小批次提交：先锁定行为与验收用例，再修改实现，最后记录前后指标。涉及 schema 的修改采用兼容迁移与逐步切换，保持旧 Worker 与新 Worker 在滚动发布期间可同时运行。优先产出顺序为 **MCP 出口防护 → 存储契约 → 阻塞工作隔离 → 运行健康与投递顺序 → 性能基线与定点优化**。
