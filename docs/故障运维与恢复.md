# 故障运维与恢复

## 先确定卡在哪一段

按同一请求的 `request_id`、`trace_id` 和外部消息 ID，依次检查入站、任务、执行、Outbox 和投递 Attempt。页面没有回复并不能说明模型没有执行。

| 现象 | 先查什么 | 处理方向 |
| --- | --- | --- |
| 机器人未连接 | Binding、Agent 就绪状态、Channel 心跳、渠道日志 | 检查账号密钥、启用状态和 SDK 错误 |
| 有处理中提示，任务还未开始 | `agent_task` 状态、前序任务、Worker 心跳与槽位 | 看排队是否来自长任务或同 Session FIFO |
| 任务运行时间较长 | 租约是否续期、模型/工具调用阶段 | 正常续租不应被另一个 Worker 重复领取 |
| 模型完成但未回复 | `outbox_message` 和 `outbox_attempt` | 区分待投递、重试、UNKNOWN、死信 |
| 同会话后续回复都停住 | 前序 Outbox 是否为 UNKNOWN | 先核对前序结果，其他会话不必一起停用 |
| MCP 搜索不到仓库 | Tool Ledger 是否存在、远端调用错误和搜索条件 | 未调用与空结果分开检查，GitHub fork 查询见重点技术 |
| RAG 更新后结果异常 | 文档 READY 状态、授权知识库、Embedding 模型 | 不把残留向量视为当前有效知识 |

## 任务接管与工作目录

Worker 按 Session 顺序领取任务。运行期间维护任务租约和 Session 执行租约；旧租约到期后允许新执行者接管，token 和 Session 版本检查阻止旧执行者提交。

暂停进程与终止进程不同。`SIGSTOP` 会让续租停止，但不会释放旧进程的文件锁。当前 Workspace ID 包含 Session、请求和执行 fence，新执行使用新目录，不删除或强抢旧锁。临时文件不在新旧目录之间自动复制，需要持久化的内容从 SQL 或 Artifact 恢复。

若结果已提交但队列完成标记尚未写入，接管者读取已完成的 Inbox/Runner 结果，复用 Outbox，不重新调用模型。若模型执行尚未提交，则仍可能需要重新执行。租约不能撤销已经发生的外部副作用，工具调用还要依赖 Tool Ledger 和服务商对账。

默认任务租约 180 秒、最多 5 次尝试；投递租约 60 秒、最多 8 次尝试。以实际运行配置为准。故障测试中的 3 秒租约只是加速配置，不能用来承诺生产 RTO。

## 投递失败怎么处理

| 状态或故障 | 当前行为 |
| --- | --- |
| 明确连接失败、可重试限流 | 有限重试，遵守 Retry-After 和退避配置 |
| 正常长时间发送 | 续期投递租约，避免被其他消费者领取 |
| 回执丢失、结果无法确定 | 标记 UNKNOWN，不自动重发 |
| PROCESSING 租约过期 | 标记 UNKNOWN，错误码 DeliveryLeaseExpired，结束原 Attempt，不新增发送尝试 |
| 永久错误或本轮重试耗尽 | DEAD_LETTER，保留错误摘要和尝试记录 |
| 旧投递者在接管后返回 | 旧租约完成或续租被拒绝 |

UNKNOWN 会阻挡同租户、Agent、Binding 和回复流中后续未完成回复，以免后发消息越过结果不明的前序消息。其他会话仍可投递。可靠性测试里的“修复后接收 1 次”，是通过不自动重发实现，不是数据库能判断远端到底是否收到。

## 人工核对入口

在租户控制台的“投递失败”中处理，也可以使用同一组 API：

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/v1/tenants/{tenant_id}/delivery-failures` | 查看 UNKNOWN 或死信记录 |
| `POST /api/v1/tenants/{tenant_id}/delivery-failures/{outbox_id}/confirm-delivered` | 已核实送达，仅更新状态，不发送消息 |
| `POST /api/v1/tenants/{tenant_id}/delivery-failures/{outbox_id}/replay` | 核实后决定重新投递 |

路径中的 `outbox_id` 是数据库 Outbox 标识，不是 payload 中的发送 ID，也不是 IM 服务商消息 ID。

确认已送达只接受当前租户的 UNKNOWN，要求 12–500 字符核实理由，可提供服务商回执：

```json
{
  "reason": "已与接收人核对，确认该条回复已经送达且内容完整。",
  "external_receipt_id": "<可选的服务商回执，未取得时省略该字段>"
}
```

操作在事务中更新 Outbox 为 DELIVERED、关联 Inbox 为 REPLIED，并追加管理审计。原 Attempt 仍保留 UNKNOWN，不伪造服务商确认。已确认或其他租户的记录不能重复确认。

重新投递只接受 UNKNOWN 或 DEAD_LETTER，必须填写原因。它将 Outbox 改为 PENDING，清零本轮 `retry_count`，保留累计 `attempt_count` 和全部历史 Attempt。不能确认是否送达时，不要把“重放”当作无风险恢复。

平台管理员进入租户范围需提供 `X-Support-Reason`。浏览器会话还需经过 CSRF 校验；直接调用 API 必须使用已有合法认证，不能绕过页面权限。

## 模型、MCP 与存储故障

- 模型配置、权限和参数错误不能靠无限重试解决。先核对活动 Profile、实际模型名、额度和错误码。
- MCP 连接成功但 Agent 没调用：检查具体工具授权、工具目录、调用风险和 Tool Ledger。GitHub 查询还要检查 fork 搜索条件。
- Tool Ledger 为 UNKNOWN：先确认外部副作用，不能通过重发用户问题绕过未知结果处理。
- Redis 异常：回源 PostgreSQL，缓存恢复后正常回填。不从 Redis 覆盖 SQL。
- PostgreSQL 不可用：入队失败时不发送应用层“已受理”提示。不要在数据库停机时手工清空幂等或租约记录。
- RAG 摄取失败：检查文档状态、文件解析、Embedding 模型及额度。旧文档向量清理失败时，查询仍按 SQL READY 来源过滤。

## 配置回滚与容量

Agent 配置以版本快照保存。发布修改稳定或灰度指针，已经入队的任务保留原 `config_version`，不会在执行中途切换。回滚配置不能回滚已经完成的外部工具操作。

扩容通过管理端写入 Worker Pool 期望节点数。先看队列等待、执行耗时和 slot 利用情况，再决定增加 slot 或 Worker。当前没有租户公平调度；持续长任务过载下，仅提高并发不能保证短任务延迟。

指标用于观察趋势，Usage Ledger 用于请求用量事实，二者不能互相替代。已有模型用量人工核对没有完整周期和总量，不据此设置生产精度承诺。

## 备份与故障域

需要保留 PostgreSQL（包括 pgvector）、对象存储和用于解密租户凭据的主密钥。三者必须配套管理。Redis、监控数据和 Workspace 不代替业务备份。

恢复前将 SQL 转储导入隔离库、核对对象清单和校验值，再进行迁移与冒烟。SQL 转储与对象清单并不是跨系统原子快照；当前文档没有经过实测的生产 RPO/RTO。批量向量重建也没有正式交付的通用运维命令。

本地开发辅助脚本在被忽略的 `dev/` 中，不视为克隆仓库即具备的运维能力。生产环境还需配置独立故障域备份、数据库高可用、对象存储容灾和告警接收。
