# 设计思路

## 平台负责什么

tRPC-Agent-Python 提供模型编排、Runner、函数工具、Skill 加载和 MCP 客户端。平台补上多租户服务所需的配置、身份、持久队列、共享状态、权限、账本和 IM 收发。

同一个租户可以配置多个 Agent 和机器人。后台管理员与 IM 对话者是两套身份：前者维护配置和权限，后者只使用机器人已获授权的能力。模型不能通过一句提示词获得另一个租户的上下文，也不能代替管理员授权工具。

| 能力 | 框架承担 | 平台承担 |
| --- | --- | --- |
| 对话执行 | LlmAgent、Runner、模型事件 | 配置快照、会话恢复、超时与失败处理 |
| 工具调用 | FunctionTool、MCPToolset | Capability Grant、风险分类、审批与 Tool Ledger |
| Skill | FsSkillRepository、SkillLoadTool | 审核目录和租户可见性，目前只加载操作知识 |
| 会话与知识 | 请求内 Session 运行视图 | PostgreSQL 事实、Redis 快照、RAG 版本与对象存储 |
| 服务入口 | Runner 接口 | 管理 API、IM Adapter、任务与投递队列 |

## 执行与收发分开

模型调用耗时不稳定，接收消息的进程不应该等待模型完成才能继续接收。Channel Runtime 先保存任务，再返回处理中提示；Worker 独立执行，回复通过 Outbox 返回 Channel Runtime。

这个拆分增加了任务和投递状态机，但也使两类失败可以分开处理。Worker 执行失败可以按任务策略重试；外部平台是否收到回复不确定时，则不能直接照搬任务重试规则。

## SQL 决定状态，缓存降低读取成本

任务是否完成、会话版本是多少、哪一个执行者有权提交，以 PostgreSQL 为准。Redis 缓存必须与 SQL 给出的 Session 版本一致，缓存丢失或异常时回源。模型请求内使用的内存 Session 不承担跨节点状态保存。

最终回复与会话变更原子提交，避免用户收到一条平台内部没有记录的业务结果。外部 IM 接收与本地回执落库不可能放在同一数据库事务里，所以投递仍有结果不明的窗口。

## 租约决定何时接管，token 决定谁能提交

租约使其他 Worker 能在旧节点失联后接管。fencing token 防止旧节点恢复后继续提交。文件锁又是另一层状态：数据库租约过期不释放进程文件锁，因此工作目录也必须按执行 fence 分开。具体故障过程见[运行时序](运行时序.md)。

结果不明的外部发送标记为 `UNKNOWN`，等待核对。这个选择牺牲了部分自动恢复速度，避免平台在没有证据时重复发送。租户可确认已送达，或在核实未送达后重新投递。

## 知识检索以文档状态为准

知识库属于租户，Agent 通过授权读取其中的指定知识库。向量只是检索候选；返回模型前还要检查 PostgreSQL 中的来源文档是否仍为 `READY`。这使文档替换、删除不依赖旧向量立即清理成功。

写操作只开放给管理 API。IM 侧的 `knowledge.list` 和 `knowledge.search` 不包含上传、删除能力。

## 当前保留的限制

- 任务队列没有租户公平轮转或长短任务分池。增加 slot 可以缓解竞争，不能保证不同租户的响应时间互不影响。
- 对没有服务商幂等或查询能力的外部写操作，不能承诺故障下的无条件 exactly-once。
- MCP 只读注解参与风险分类，但远端服务仍需使用合适权限的凭据；客户端授权不能替代服务端权限。
- Workspace 是执行临时空间，不是容器沙箱。Skill 只加载知识说明，不执行脚本。
- 当前向量列固定为 1024 维。更换 Embedding 模型需要重新索引，不能仅改模型名称后继续混用旧向量。
- 本地和 Docker Desktop Kubernetes 验收不等于生产高可用。数据库容灾、对象存储备份、TLS 和实际告警接收需要部署环境提供。

已完成的验证和仍不能推出的结论见[测试结果](测试结果.md)。
