## 性能测试

### 环境与测量方法

- 工具：Locust 2.46.6，Python 3.12.13。
- 主机：WSL2，i7-12700H，20 个可见逻辑 CPU，约 7.6 GiB 内存。
- Worker：同机独立 Python 进程，每进程配置 1 或 2 个 slot。
- 数据：专用测试数据库，真实 PostgreSQL 队列、Pipeline、Session/Outbox 持久化，Redis Session 缓存开启。
- 链路：规范化请求提交到任务完成。不包含外部 IM 收发、Gateway 接入、RAG/MCP、媒体处理和跨机器调度。
- 模拟场景仅将 Runner 替换为固定等待，其余使用生产实现。每组预热 30 秒、测量 120 秒，再排空已提交任务。延迟排除预热样本。

吞吐统计业务任务完成数与对应时间窗口。模拟容量表使用测量窗口统计；真实短批次提前达到请求上限后结束，吞吐以首个提交到最后完成观测的实际批次时长计算。

总耗时从压测端提交到观察到完成，包含排队、执行、持久化和完成轮询，轮询间隔最多约 200ms。排队耗时取 `started_at - created_at`。这里的 P95 不是模型首 token 延迟，也不是 IM 用户收到整条回复的时间。

P95 使用 nearest-rank：将耗时排序后取第 `ceil(样本数 × 0.95)` 个值。真实对照每组 19 次，因此该组 P95 实际等于组内最大耗时。

### 真实 LLM 对照

模型为 `qwen3.7-flash`，关闭 thinking，temperature 为 0，最大输出 128 tokens。固定输入“计算17乘23，只回复数字。”，每次新 Session，实际输入 48、输出 3 tokens，答案均为 `391`。这是同一个问题的重复链路验证，不是 120 道不同题目的准确率测试。

每个 Worker 配置 1 个 slot，每个对照批次 19 次请求：

| 并发 | 单 Worker 吞吐（请求/秒） | 双 Worker 吞吐（请求/秒） | 单 Worker 总耗时 P95 | 双 Worker 总耗时 P95 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 1.199 | 1.230 | 1.242 秒 | 1.246 秒 |
| 2 | 1.823 | 2.275 | 1.471 秒 | 1.255 秒 |
| 4 | 1.764 | 3.253 | 2.729 秒 | 1.683 秒 |

并发 4 时，吞吐提升 84.4%，P95 降低 38.3%。样本少、输出短，结论仅限这次对照。共 120 个真实业务请求：1 次预检、6 组各 19 次、5 次 HTTP 计数验证。每次均得到正确答案并生成唯一回复，Usage Ledger 共记录 6,120 tokens。

前 115 次请求的 SDK HTTP 尝试计数未成功采集，原因是 SDK 使用 `httpx2`，原计数器只拦截 `httpx`。最后 5 次确认有 5 次 HTTP 200。不能把“120 次业务成功、无 Worker 重试”写成“120 次均无 SDK 重试或限流”；6,120 tokens 也没有在这一轮独立核对供应商账单。

### 模拟容量对照

固定 2 秒任务、并发 8，每请求使用新 Session，单、双 Worker 各跑三轮：

| 配置 | 三轮吞吐（请求/秒） | 吞吐中位数 | 总耗时 P95 范围 |
| --- | --- | ---: | ---: |
| 1 Worker × 1 slot | 0.475 / 0.475 / 0.475 | 0.475 | 16.94–17.02 秒 |
| 2 Workers × 1 slot | 0.933 / 0.950 / 0.950 | 0.950 | 8.48–8.63 秒 |

单槽位理论上约每 2 秒完成一项任务，因此接近 0.5 请求/秒；增加为两个槽位后接近 1 请求/秒。中位数恰好为两倍，不代表增加 Worker 在所有场景下都能线性扩展。这组数据验证的是调度与执行槽位扩展，不是模型速度。

容量矩阵共 24 组、3,143 次请求，测试并发为 1、2、4、8、16。最高测试到 16 不等于系统最大并发为 16，也没有测到硬件极限。

### 租户竞争

A 租户任务模拟执行 8 秒，B 租户任务模拟执行 0.2 秒。B 固定每 5 秒提交一次。固定 A 到达率为 0.15 请求/秒，每组 B 有 24 个测量样本：

| 配置 | B 排队 P95 | B 总耗时 P95 | 停止提交后的排空时间 |
| --- | ---: | ---: | ---: |
| 1 Worker × 1 slot | 41.970 秒 | 42.364 秒 | 45.37 秒 |
| 1 Worker × 2 slots | 1.612 秒 | 2.076 秒 | 4.80 秒 |
| 2 Workers × 1 slot | 1.592 秒 | 2.066 秒 | 4.81 秒 |

42.364 秒降至 2.066 秒，降幅约 95.1%，统计的是 B 的短任务。它与前面的“固定 2 秒任务 P95 约下降 50%”是两组不同负载，且都不是实际模型任务。改善主要来自减少排队；B 在双 Worker 下仍慢于独立运行基线。

当前队列没有租户公平轮转，跨租户资源竞争仍然存在。该部分共 15 组、765 次请求。

### 4,028 次的统计边界

`3,143 + 765 + 120 = 4,028`。模拟总数包括预热阶段提交的请求，但性能延迟统计排除了预热。另有 291 条此前中断、冒烟与恢复任务记录，不纳入本轮，其中存在一次租约到期恢复重试。“本轮失败为 0”不覆盖那些记录，也不包括刻意制造失败的可靠性测试。

## 可靠性复测

使用真实 PostgreSQL、生产队列与 Worker 子进程。投递端由本地 HTTP 服务注入错误；企业微信使用实际 SDK 和正式适配器连接本地 WebSocket 服务端。测试将租约缩短到 3 秒加速故障，不将这些时间作为生产恢复 SLA。

| 编号 | 场景 | 结果 |
| --- | --- | --- |
| 1 | 同一外部消息 ID 并发入队 50 次 | 1 个任务、1 次 Runner 执行、1 条 Outbox；相同 ID 的冲突正文被拒绝 |
| 2 | 两租户使用相同外部消息 ID | 各自生成独立任务与所属租户的回复 |
| 3 | 两 Worker 竞争同 Session 的 3 个任务 | 同会话按顺序执行，另一个租户的会话可前进 |
| 4 | 8 秒任务使用 3 秒租约 | 持续续租，只有 1 次执行尝试 |
| 5 | Runner 执行中 SIGKILL | 第二次尝试完成，最终只有 1 条 Outbox |
| 6 | 共享根目录，旧 Worker SIGSTOP | 新 fence 使用独立目录，第二次尝试完成；旧提交、旧续租被拒绝 |
| 7 | 每节点独立目录，旧 Worker SIGSTOP | 对照场景通过，同样拒绝旧 token |
| 8 | SIGTERM 排空 | 当前任务完成后正常退出，不启动第二次执行 |
| 9 | 真实模型重复消息与新消息 | 30 次重复入站和完成后 10 次重放只调用原模型 1 次；相同文字的新消息 ID 正常再调用 1 次 |
| 10 | 模型结果和 Outbox 提交后、任务完成前崩溃 | 2 次任务尝试、1 次模型 HTTP 调用、1 条 Outbox、1 条 Usage Ledger |
| 11 | 投递端连接拒绝后恢复 | 第二次尝试成功，接收端只接受 1 次 |
| 12 | 接收成功但回执丢失 | 转 UNKNOWN，禁止自动重发，阻挡同回复流的后续消息 |
| 13 | 12 个 Delivery Worker 实例并发领取 | 1 次成功领取，接收端接受 1 次；不是 12 台机器 |
| 14 | Retry-After、永久失败与人工重放 | 遵守退避时间，永久失败进入死信，重放只重置本轮重试预算 |
| 15 | 接收成功但未记账，投递租约过期 | 修复前接收 2 次，修复后接收 1 次并转 UNKNOWN |
| 16 | 4.5 秒发送使用 3 秒租约 | 正常续租，没有被错误隔离为 UNKNOWN |
| 17 | 实际 Uvicorn HTTP 确认已送达 | 校验身份、租户、理由、重复操作和审计；不重发，放行后续回复 |
| 18 | 企业微信 SDK 断连重连、重复回调 | 2 次鉴权、2 次重复回调，对应 1 个任务和 1 个最终回复帧 |

第 6 项修复前因旧目录持锁耗尽 5 次执行尝试，修复后首次接管成功，即总尝试次数为 2。第 15 项改为保守核对后，不再自动重发不确定结果；需要人工处理的代价仍然存在，不能描述成无条件 exactly-once。

18 项按最新有效结果去重。首次 HTTP 管理流程用例把 Outbox 主键与 payload 发送 ID 混用，修正测试脚本后单独复跑通过，没有把多次重跑累计为更多独立场景。本轮可靠性真实模型调用共 3 次 HTTP 200，账本记录 153 tokens，与压测的 120 次分开统计。
